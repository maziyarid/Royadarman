## 1. Governing rule: correct and extend the existing platform

Royadarman must **not** be rewritten into Node/Nest/Fastify, PostgreSQL/PostGIS, or microservices merely because earlier proposal text mentioned those technologies. The implemented and deployed system is Laravel 13 on PHP 8.3 with MariaDB/MySQL-family storage, Blade/Vite/Tailwind frontend assets, database-backed sessions/queues, and an established security model around OTP/MFA, clinical-document quarantine/scanning, consent, policies, audit events, and release preflight.

The correct direction is:

> **Harden, formalize, and improve the existing Laravel modular monolith.**

Extract a service only when measured scale, reliability, deployment cadence, or team ownership creates a concrete reason.

## 2. Product position and clinical boundary

Royadarman is a **Persian-first dental access, discovery, referral, coordination, and CRM platform for Tehran**.

It coordinates:
- dental guidance and intake;
- clinic and clinician discovery;
- referral and follow-up;
- Tehran home-dentistry requests;
- preliminary OPG review assigned to licensed clinicians;
- patient/clinic/coordinator communication;
- operational CRM and service follow-up.

Royadarman itself is not the diagnosing or treating clinician. Clinical conclusions, image interpretation, diagnosis, prescriptions, and treatment decisions must be attributable to an appropriately licensed clinician. OPG review remains preliminary and must not be presented as definitive diagnosis.

Maintain four explicit boundaries:
1. **Coordination** — intake, matching, referral, dispatch, communication, follow-up.
2. **Clinical care** — examination, diagnosis, treatment planning, image interpretation, prescriptions, clinical escalation.
3. **Practice operations** — clinic branches, schedules, capacity, staff, service records, future quotations/payments if introduced.
4. **Growth CRM** — inquiries, attribution, recall, reactivation, treatment-plan follow-up, abandoned-request recovery.

## 4. Persian-first experience and design system

Persian is the source language, not a later translation. Arabic and English are supported secondary locales.

The UI must be redesigned around the clarity of modern local mobility/service apps: one obvious next action, progressive disclosure, large touch targets, clear service cards, location selection, map/list discovery, visible status progression, and mobile-first layout.

### Mandatory brand tokens from the existing logo
- Primary blue: `#2947A3`
- Deep blue: `#162B70`
- Accent orange: `#F2A566`
- Warm off-white: `#F7F5EF`
- Neutral ink/background tokens derived from the current CSS

Do not invent an unrelated palette.

### UX principles
- prominent `چه خدمتی نیاز دارید؟` / “What do you need?” entry point;
- service-first, not clinic-first, patient journey;
- explicit Tehran location/neighborhood selection with manual fallback when geolocation is unavailable;
- map + list presentation when discovery data is available;
- clear explanation of why a provider/branch is suitable;
- step-by-step request progress instead of long forms;
- obvious routine vs urgent distinction;
- Jalali-aware Persian presentation where appropriate while preserving machine-readable Gregorian timestamps;
- Persian numerals and local phone/address conventions in UI where appropriate;
- accessible contrast, keyboard support, focus states, and reduced-motion-safe interactions;
- skeleton/loading/error/empty/success states designed for every major workflow;
- mobile-first responsive PWA-quality web before native apps.

### Imagery policy
Use licensed stock or generated images where they materially improve comprehension and trust. Images must:
- be traceable to a license/source or be generated specifically for Royadarman;
- avoid implying that stock models are Royadarman clinicians or actual patients;
- include useful Persian alt text;
- use responsive WebP/AVIF outputs where practical;
- avoid graphic intraoral imagery on general public surfaces;
- align with the brand palette and healthcare-support tone.

## 5. Patient access and discovery

The primary patient flow asks what the patient needs before asking which clinic they know.

Collect only what is necessary for the selected service:
- service type;
- routine/urgent indicator;
- Tehran neighborhood/location;
- preferred time;
- accessibility/mobility needs;
- language/communication preference;
- budget range when relevant;
- home-care requirement;
- whether an OPG already exists.

### Discovery model
Clinical/service suitability is a gate. Distance is a ranking factor, not the first filter.

Conceptual ranking:

```text
rank = clinical_fit
     + availability
     + travel_time
     + patient_preferences
     + verified_quality
     + affordability
     - operational_risk
```

Implement Tehran geo matching with plain latitude/longitude columns, indexed bounding-box filtering, and Haversine distance. **Do not introduce PostGIS** unless a future verified need justifies a database migration.

Show:
- neighborhood and approximate distance;
- estimated travel time when a mapping adapter is configured;
- next suitable response/appointment window;
- verified services/specialties/equipment;
- home-visit coverage;
- price ranges only when current/reliable;
- verification freshness;
- concise reasons for suitability.

## 6. Core bounded domains

### Identity and sessions
Preserve the existing OTP + staff MFA model. Add first-class session inventory and revocation using Laravel's existing database sessions. Sensitive account changes should revoke other sessions automatically.

### Clinic and provider network
Model organizations, branches, clinicians, specialties, services, equipment, service areas, verification status, hours, and capacity. Do not expose unverified partner data as authoritative.

### Referral lifecycle
Use explicit states and append-only events, with SLA timers, clinic acceptance/decline, coordinator override, escalation, and closure. No silent case disappearance.

### Appointment requests
Add requests/holds/confirmation only when the source of availability is defined. Use transactions and idempotency. Never display “confirmed” based solely on an unacknowledged local write when a partner system is system-of-record.

### OPG workflow
Preserve the existing fail-closed clinical-document pipeline. Add monitoring, health checks, assignment, structured clinical review, sign-off, patient-safe summary, and urgent escalation. Do not add autonomous diagnosis in the initial release.

### Home dentistry
Keep a separate Tehran-only eligibility/dispatch workflow. Protect exact address until necessary, validate coverage, match staff/equipment/capability, and provide explicit urgent/hospital escalation.

### CRM
Add separate operational pipelines for inquiry, referral, OPG, home visit, recall/reactivation, treatment-plan follow-up, and abandoned requests. Every task has owner, next action, channel, outcome, and loss reason.

## 7. Role model and dashboards

Least privilege remains mandatory.

Target roles:
- Patient
- Coordinator
- Clinician
- Clinic manager / clinic representative
- Reception (new scoped role when scheduling is implemented)
- Owner / business administrator
- Technical administrator
- Compliance reviewer (new controlled read-only role)

Dashboard UX should use task-oriented cards/timelines rather than raw database tables.

Key role capabilities must be enforced server-side through policies and tests. Replicate the fail-closed `ClinicalDocumentPolicy` pattern for referrals, home dentistry, appointments, CMS media, and sessions.

## 8. API and mobile strategy

Current authenticated `/api/v1` routes are first-party session + CSRF APIs. Document and test this explicitly.

Future native mobile clients should use an additive Laravel Sanctum guard under a clearly separated namespace such as `/api/v1/mobile/*`. Do not replace the existing web/session guard.

All identity guards must reuse the same OTP/staff-MFA verification logic.

Patient mobile/PWA experience comes first. Coordinator comes second. Clinician remains responsive web until there is a concrete mobile requirement.

## 9. Security priorities

### P0: CMS media boundary
Current CMS media accepts SVG/GIF and derives storage from upload metadata. Fix this before expanding CMS usage:
- reject SVG by default;
- restrict to JPEG/PNG/WebP unless a future business case is approved;
- inspect file bytes server-side;
- re-encode raster images to WebP/AVIF to remove metadata/polyglot payloads;
- generate server-side random filenames;
- apply size/dimension limits;
- add positive and spoofed-extension regression tests;
- consider a cookieless media origin if active formats are ever supported.

### Preserve the clinical-document pipeline
Do not rewrite the proven quarantine → hash → ClamAV → re-hash → approve → authorized streaming lifecycle. Add scheduled EICAR/clean-file health tests and monitoring.

### Session compromise response
Add list/revoke/revoke-all capabilities, privileged action audit, automatic revocation after sensitive identity changes, and a documented incident runbook.

### Staging separation
Maintain separate credentials, database, keys, storage, and noindex controls. Staging uses only synthetic/de-identified data and must never send real SMS or real partner notifications.

## 10. CI/CD and repository governance

### Mandatory changes
1. Commit `backend/package-lock.json` and use `npm ci`.
2. CI must build/test `backend/resources` — never the obsolete `Front-end v1` tree.
3. `composer audit --locked` becomes blocking; documented temporary exceptions only.
4. Add `npm audit --audit-level=high` for the real frontend build.
5. Add a MariaDB service-container migration job in addition to SQLite tests.
6. Add browser-level E2E tests (Playwright or Dusk) for primary patient/staff journeys and security boundaries.
7. Add explicit session/CSRF/webhook-signature tests.
8. Protect `main`: reviewed PRs + required completed checks + no force pushes.
9. Add Dependabot or Renovate.
10. Record release SHA, preflight result, migration status, and asset build hash in a release manifest.

## 11. Infrastructure as code

Move host-only operational knowledge into `infra/`:
- queue worker config;
- scheduler cron source;
- ClamAV configuration and verification fixtures;
- deploy and rollback scripts;
- staging deployment script;
- documented PHP binary/runtime paths;
- backup/restore runbooks.

Deployment must fail closed if tests, dependency audit, frontend build, migrations, or `royadarman:preflight` fail.

## 12. Staging and presentation architecture

`staging.royadarman.com` is a presentation/QA environment, not a shortcut into production.

Requirements:
- isolated synthetic database and secrets;
- Persian default;
- global `noindex,nofollow,noarchive` and crawler block;
- valid TLS;
- no real SMS, email, payment, clinic webhook, or patient data;
- presentation portal with role-switching convenience;
- role handoff must not expose permanent production bearer credentials;
- interactive patient journey with deterministic staging OTP;
- reset/reseed command so testers can safely mutate data and return to baseline;
- visible `محیط آزمایشی` banner on all authenticated staging pages;
- automated smoke test covering all six presentation roles and primary public pages.

## 13. Observability and quality metrics

Track at least:
- inquiry response time;
- search-to-request conversion;
- referral acceptance/completion;
- clinic response SLA;
- failed handoffs;
- OPG upload/scan/review turnaround;
- home-visit completion/cancellation;
- notification failure rate;
- stale clinic data;
- queue depth/failed jobs;
- API latency and 5xx rate;
- release/preflight status.

Use privacy-preserving aggregate telemetry; never place clinical content or raw PII in analytics events.

## 15. Non-goals

Do not:
- rewrite Laravel into Node/Nest/Fastify;
- replace MariaDB with PostgreSQL/PostGIS without a measured need;
- split microservices prematurely;
- add autonomous OPG diagnosis;
- claim payments, insurance, charting, or practice-management capabilities that are not implemented;
- use the historical frontend trees as production source-of-truth;
- weaken production authentication to simplify demos;
- use permanent bearer demo URLs on production.
